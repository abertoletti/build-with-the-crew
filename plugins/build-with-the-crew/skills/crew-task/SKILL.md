---
name: crew-task
description: Carry an assigned development task through analysis, implementation, independent review, QA, corrections and pull request integration inside its own Git worktree.
---

Use the assigned chat, native goal, worktree, task ID and base. Before editing, check the actual repository, branch and task record. Locate the installed plugin two directories above this skill's real path. In a prepared cloud environment the launch brief can supply the bundle path. Use `node <plugin>/scripts/method.mjs config` to resolve project roles.

Run `method.mjs doctor` from this checkout at startup to inventory the skills. Before starting each native role, repeat `method.mjs doctor ROLE` and use the returned `available` paths. Ask the specialist to open the listed `SKILL.md` files in its own environment, follow the relevant resources and identify the files it used in its handoff. Do not accept role work if the assigned skill could not be read. Report optional warnings to the coordinator. If a required skill is unavailable for a participating role, put the task in `waiting-human` and route a decision through the coordinator with the role, skill, environment and suggested fix. Resume only after a successful repeat check or an authorized config change. For the independent reviewer the `review` command checks the actual PR base skill versions before spending a round. For external tools, report CLI or dependency failures from the adapter and never substitute a provider or a skill silently.

When a native specialist role has an explicit `effort`, use the host's agent tool with `reasoning_effort` set to that value. Pass the role, selected skills and task context directly when a fresh context is required for an override. If work stays inline, use it for this role only when the task chat's actual effort matches. If the host cannot apply or confirm the requested setting, report the limitation and pause that role. UX and review commands take their settings from the project configuration.

1. **Analysis and design.** Convert the assignment to observable acceptance criteria. Use the analyst, the architect for architecture decisions, and the UX specialist for interface work. Delegate independent work where supported. For Claude UX, use the external adapter as described in [external specialists](references/specialists.md). Record decisions that change the implementation. Pause this task when an essential user decision is missing.
2. **Develop and verify.** Work only in this task's checkout. Use the configured development skills for behavior changes and fault investigation. Run the project's test commands with QA against the actual revision, retaining the commands and results. Open or recover the task's existing PR on the configured base. Inspect the actual diff before transmitting it to the configured reviewer under the user's authorization.
3. **Review and correct.** Use `node <plugin>/scripts/method.mjs review OWNER/REPO PR BRIEF_FILE` in the task worktree at the exact PR head. Include acceptance criteria and test evidence in the brief. A reviewer requesting changes sends the task back to development. Re-run tests, push the fix, fetch the current base, and request a new review of the new commit. A missing or unverifiable review stops integration. Surface a persistent failure or an exhausted review budget to the coordinator.
4. **Deliver.** In `ready` mode leave the reviewed PR open. With named CI checks, run `verify OWNER/REPO PR` before reporting it ready. With no checks configured, report independent review and local test results, and flag CI readiness as unverified. In authorized `merge` mode, run `merge OWNER/REPO PR`, confirm the server result and record the merge commit. GitHub rulesets and branch protection govern server-side integration.
5. **Resume safely.** Record each material transition using `checkpoint ID EXPECTED_REVISION STAGE NOTE_FILE`. Use `status ID` and `history ID` to recover the thread, branch, last SHA, PR, unresolved questions and review round. If a concurrent writer advances the revision, reconcile before retrying. Use stable task IDs, existing PRs and exact commit IDs. A paused task can resume after the human decision without affecting other tasks.

At the first worktree checkpoint, pass an optional JSON file after `NOTE_FILE` with the actual `branch` and `worktree`, and `threadId` if available. Include `prNumber` (an integer) when the task opens or recovers its PR. Checkpoint `review`, `testing` and `waiting-human` when entering those stages so the local dashboard can report them.

After the host confirms a native subagent launch, record `method.mjs agent-event TASK_ID AGENT_ID agent-running LABEL`. When its result is observed, use the same ID and label with `agent-done` or `agent-failed`. If the journal is inaccessible, report the actual agent event in the task chat. An event is an observation, never a claim about what the agent is thinking.

## Ask through the coordinator

For a product or implementation decision that needs the user, write a JSON request with `question`, `options` (an array of strings), and optional `recommendation`. Use a stable lowercase decision ID, distinct for each question. Register it using `method.mjs decision-request TASK_ID DECISION_ID FILE`, record `waiting-human`, and hand it off to the coordinator. Use the host's authorized notification mechanism if available. In your final answer include one line beginning `CREW_DECISION ` followed by a JSON object with `taskId`, `decisionId`, `question`, `options` and optional `recommendation`. Include the same IDs even when the coordinator uses a separate journal. Leave the overall goal incomplete if its criteria still depend on the decision. Native approval prompts and security confirmations still follow the host's approval flow.

When the coordinator forwards a decision, verify the task and decision IDs against the local request. Record the answer using `decision-answer TASK_ID DECISION_ID FILE`. If the task was waiting on this decision and can proceed, record a `working` checkpoint. Acknowledge receipt using `decision-ack TASK_ID DECISION_ID`, emit `CREW_DECISION_ACK {"taskId":"...","decisionId":"..."}`, and repeat the acknowledgement in the final answer so the coordinator can reconcile it. Report any remaining blockers separately. On a repeat delivery, check the latest checkpoint and continue only unfinished work. Take conflicting answers back to the coordinator.
